# MediaWatch — техническая документация проекта

Этот файл — полная техническая картина проекта: архитектура, схема БД,
протоколы всех видеобалансеров (включая факты, установленные экспериментально,
а не по документации — у большинства из них официальной документации нет),
известные ограничения и незакрытые вопросы. Пишется как самодостаточный
источник для переноса контекста в другую сессию/модель.

Для быстрого старта (установка, .env) см. [README.md](README.md).

---

## 1. Что это за проект

Веб-сайт для просмотра **аниме** и **фильмов/сериалов** с кросс-девайс
синхронизацией позиции просмотра (тайтл → сезон → серия → секунда,
сохраняется в облаке и восстанавливается на любом устройстве после входа).

Сайт **сам не хостит видео** — встраивает чужие видеобалансеры (iframe-плееры
сторонних сервисов) по токенам/API, аналогично тому, как это делают многие
легальные агрегаторы. У каждого балансера свой уровень интеграции — от
точного трекинга позиции через `postMessage` до банальной вставки iframe.

## 2. Стек

- **Next.js 14** (App Router, Server Components) + **TypeScript** + **Tailwind CSS 3.4**
- **Supabase** — Postgres + Auth + Row Level Security + Realtime
- **Vercel** — хостинг + Cron Jobs (без отдельного Node-сервера)
- Внешние источники контента: **Shikimori** (метаданные аниме), **AniLibria**
  (прямой HLS-поток для аниме), **Videoseed** (каталог + плеер кино),
  **Vibix**, **Kodik**, **YummyAnime** — балансеры/плееры
- Шрифт — **Inter** (`next/font/google`, self-hosted)

## 4. Схема данных (Supabase Postgres)

Миграции применяются **вручную** (нет CI-автоприменения) — новую миграцию
нужно самостоятельно выполнить в Supabase SQL Editor после того, как код
задеплоен.

### `watch_progress` (0001, 0002, 0003)
Одна строка на пару (пользователь, тайтл). Позиция просмотра для UI
«Продолжить просмотр» и восстановления при открытии серии.

```
user_id, content_type ('anime'|'cinema'), shikimori_id (для cinema — kinopoisk_id!),
anime_title, poster_url, season (default 1), episode,
position_seconds, duration_seconds, translation_id, updated_at
unique (user_id, content_type, shikimori_id)
```

⚠️ Колонка называется `shikimori_id` даже для кино (исторически) — там в ней
лежит **kinopoisk_id**. Не переименовано намеренно, чтобы не трогать рабочий
путь аниме.

### `user_list` (0001, 0002)
Пользовательский список: `watching | planned | completed | dropped`.
`unique (user_id, content_type, shikimori_id)`.

### `watched_episodes` (0004)
Точная пометка каждой досмотренной серии (для подсветки в сетке серий и
автоперевода тайтла в «Просмотрено» по окончании последней серии).
`unique (user_id, content_type, shikimori_id, season, episode)`.

### `episode_notifications` + `title_episode_baseline` (0005)
Уведомления о новых сериях (см. §8). Первая таблица — персональная (RLS),
вторая — глобальный кэш, полностью закрыта от клиентов (RLS без единой
policy — доступна только через `service_role`).

Все таблицы — RLS `auth.uid() = user_id` на select/update/delete. **Insert
через клиента запрещён** там, где строки должен создавать только сервер
(`episode_notifications` — только крон; остальные — через клиентский upsert
под RLS, это нормально).

### `resolved_streams` (0007)
Кэш прямых видео-ссылок для собственного плеера (§12). RLS без единой
policy — как `title_episode_baseline`, доступна только через `service_role`
(в ней лежат «сырые», без хотлинк-защиты на нашей стороне, ссылки апстрима,
клиентам их видеть незачем и небезопасно).

## 5. Прогресс просмотра — общая архитектура

Единая точка записи — `POST /api/progress` (`src/app/api/progress/route.ts`).
Принимает несколько режимов через один и тот же endpoint:

- **Обычная запись** — `position_seconds`, `duration_seconds`, `translation_id`.
  Отбрасывает записи с `position_seconds < 5` (случайные открытия).
- **`mark: true`** — отметить серию открытой БЕЗ точной позиции (для
  источников без трекинга — Videoseed, Alloha/Sibnet/Aksor через Yummy).
  Не перезаписывает уже сохранённую точную позицию той же серии.
- **`watched_episode: true`** — записать серию в `watched_episodes` (upsert,
  `ignoreDuplicates`).
- **`completed: true`** — перевести тайтл в `user_list` со статусом
  `completed`.

Клиентский хук `useProgressSaver` (`src/hooks/useProgressSaver.ts`) —
общая логика для HLS/Kodik-подобных источников: сохраняет каждые 10 сек во
время воспроизведения + на `beforeunload`/`visibilitychange` (через
`sendBeacon`, чтобы не терять данные при закрытии вкладки).

Realtime-синхронизация между устройствами: подписка на `postgres_changes`
таблицы `watch_progress`, тост «на другом устройстве вы перешли на серию X»
(показывается только когда вкладка неактивна/на паузе, чтобы не сбивать
активный просмотр).

## 6. Видеоисточники — аниме

Оркестратор — `src/components/WatchPlayer.tsx`. Три источника, переключатель
показывает только реально доступные для конкретной серии:

### AniLibria (приоритет по умолчанию, если найден)
- **Выполняется в браузере**, не на сервере (`src/lib/anilibria.ts`) —
  намеренно, чтобы поток шёл с гео-привязкой по IP пользователя.
- Внешних id (Shikimori/MAL) в их API нет → сопоставление тайтла эвристикой
  по названию (ромадзи + русское) + год, порог строгий (`score >= 80`),
  лучше не найти, чем сыграть чужой тайтл.
- Отдаёт **прямые HLS-ссылки** (1080/720/480p) → рендерится через `hls.js` в
  собственном `<video>` (`HlsPlayer.tsx`). Единственный источник с полным
  контролем над плеером: точный `timeupdate`, кнопка «Пропустить
  опенинг/эндинг» (тайминги — из YummyAnime, см. ниже), качество без
  перезагрузки страницы.

### Kodik (второстепенный/резервный)
- Серверный поиск по `shikimori_id` (kodik-api.com/search) — точный, не
  эвристика.
- Протокол `postMessage` **документирован и надёжен** —
  `src/lib/video/kodik-events.ts`: `kodik_player_time_update`,
  `kodik_player_duration_update`, `kodik_player_play/pause/video_started/
  video_ended`, `kodik_player_current_episode` (смена серии внутри плеера).
- Восстановление позиции — параметр `start_from` в query embed-URL.
  **Подтверждено экспериментально** (см. §7), что этот параметр
  обрабатывается **на сервере Kodik**, а не в клиентском JS — при статическом
  анализе бандла плеера строка `start_from` не встречается, что раньше
  привело к ложному выводу о неработоспособности параметра. Реальная
  проверка: сравнение HTML-ответа с разными значениями параметра — сервер
  вставляет `parsedStartFrom = parseStartfrom("N")` в разметку.

### YummyAnime (третий, опциональный)
- `src/lib/video/yummy.ts`, публичный API без токена, сервер `api.yani.tv`.
- Точный матчинг по `?shikimori_ids=` (батч, без обрезки).
- `/anime/{id}/videos` отдаёт **не поток**, а `iframe_url` на другие
  балансеры (Kodik/Alloha/Sibnet/Aksor) — на выборке ~57% строк это
  `kodikplayer.com`. Дедупликация по `iframe_url` (Alloha отдаёт несколько
  «озвучек» под одним и тем же iframe — выбор внутри их плеера).
- Трекинг: если выбранная строка — Kodik-эмбед, включается тот же протокол
  `KODIK_EVENTS` + `start_from` для резюма. Если нет (Alloha/Sibnet/Aksor) —
  **точный трекинг невозможен**: проверено эмпирически (скачаны все JS-бандлы
  плеера Alloha, ~1 МБ суммарно, — **ноль** упоминаний `postMessage`/
  `MessageEvent`), только `mark: true`. Alloha требует `Referer` со своего
  домена (`yani.tv`) — иначе отдаёт страницу-заглушку (обычная
  хотлинк-защита, не связана с трекингом).
- Также источник **skip-таймингов** опенинга/эндинга для AniLibria-плеера
  (`skips.opening/ending`, приоритет — строка с озвучкой «AniLibria», она
  точнее всего совпадает по монтажу с нашим HLS-потоком) и **постеров**
  лучшего качества, чем у Shikimori (см. §7).

### Наш плеер (четвёртый, опциональный — когда доступна Alloha)
`OwnPlayer.tsx` — собственный плеер с полным контролем (см. §12): сервер
извлекает у Alloha-эмбеда прямую ссылку и Range-проксирует её напрямую в
`<video>`/`hls.js`, без стороннего iframe. За счёт этого — точный
`timeupdate`, те же кнопки пропуска опенинга/эндинга, что и у HLS-плеера.

## 7. Видеоисточники — кино (фильмы и сериалы)

Оркестратор — `src/components/Player.tsx` (отдельный от `WatchPlayer.tsx`,
не переиспользуется). Три источника по приоритету:

### Vibix (по умолчанию — единственный с полным точным трекингом)
- `src/lib/video/vibix.ts`. REST `https://vibix.org/api/v1/publisher/
  videos/kp/{kpId}`, `Authorization: Bearer $VIBIX_TOKEN` (формат токена
  `id|секрет`, приватный, только сервер).
- `iframe_url` в ответе **пустой** — встройка через их SDK: тег
  `<ins data-publisher-id data-type data-id [data-season] [data-episodes]>`
  + скрипт `graphicslab.io/sdk/v2/rendex-sdk.min.js`, который сам создаёт
  iframe (`VibixPlayer.tsx`).
- Протокол `postMessage` **реальный, но НЕ соответствует их же официальной
  sync-библиотеке** (проверено логом): плоский нативный формат Playerjs
  `{event, time, data, duration}`, а не `{type:'playerEvent', ...}`, который
  описан в их sync-lib.js. `time` летит ~4 раза/сек. Origin iframe —
  `*.kinescopecdn.net`. Команда возврата позиции — нативный Playerjs
  `{api:'seek', set:N}` (дублируем и `{type:'playerCommand', ...}` про
  запас). Важно: плеер сам восстанавливает СВОЮ локальную позицию ДО события
  `started` — наш seek из БД шлётся именно на `started`/`play`, не раньше,
  иначе он будет перебит их собственным резюмом.

### Videoseed (второй; каталог + плеер)
- Плеер: `src/lib/video/videoseed.ts`, embed_auto по kinopoisk_id
  (`VIDEOSEED_TOKEN`). Каталог (список/поиск/карточка): `src/lib/
  videoseed-catalog.ts`, apiv2.php (`VIDEOSEED_API_TOKEN` — **другой** ключ,
  «Ключ API», не «Ключ API плеера»).
- **Ключевой факт**: их Playerjs 22.0.1 — с **ВЫКЛЮЧЕННОЙ** опцией «Plugins /
  API / postMessage for iframe» (проверено эмпирически: 0 сообщений в window
  при play/pause/seek). Точная позиция физически недоступна.
- Вместо неё — эвристический оценщик `src/hooks/useVideoseedEstimator.ts`:
  ловит клики внутрь iframe через `window.blur` + `document.activeElement`,
  учитывает fullscreen, копит время таймером, потолки по длительности.
  Резюм — с буфером −15 сек (лучше начать чуть раньше, чем позже).
  Диагностика: `localStorage['aw:debugPlayer'] = '1'` → логи `[player msg]`.
- Пользователь писал в поддержку Videoseed (Telegram @Doznet) с просьбой
  включить postMessage — если включат, оценщик можно заменить точными
  событиями.

### Kodik (третий, резервный)
Тот же клиент/протокол, что и в разделе аниме (`src/lib/video/kodik.ts`,
`kodik-events.ts`), поиск по `kinopoisk_id` вместо `shikimori_id`.

### Наш плеер (четвёртый, опциональный — когда доступен Videoseed)
`OwnPlayer.tsx` — тот же механизм, что для Alloha в разделе аниме (см. §12),
но извлекает ссылку у Videoseed-эмбеда. В отличие от обычного Videoseed
(iframe без событий, только эвристическая оценка позиции, см. ниже) — тут
позиция и вся навигация точные, потому что видео идёт напрямую в наш
`<video>`, а не в чужой iframe.

### Сезоны
`videoseed-catalog.ts` парсит `seasons[]` из ответа Videoseed
(`{season, episodes}`). Роут — `/cinema/watch/[id]/[season]/[episode]`
(сезон — часть пути, не query-параметр). Переход между сериями умеет
пересекать границу сезона (последняя серия сезона → первая серия
следующего).

### 7.1. Каталог и фильтры кино

У Videoseed НЕТ рабочей серверной фильтрации/сортировки — параметры
`categories`/`category`/`genre`/`country` либо отдают HTTP 500, либо
принимаются, но реально ничего не фильтруют, `sort_by` тоже не работает
(наблюдался фактически алфавитный порядок вместо `post_date desc`).
Проверено вживую. Поэтому фильтрация по жанру/стране реализована ЦЕЛИКОМ на
нашей стороне, в `getCinemaCatalog()` (`src/lib/videoseed-catalog.ts`) —
`MAX_UPSTREAM_PAGES=30` защищает от лавины запросов апстрима на редкий жанр
при глубокой пагинации.

Старые именованные категории (`CINEMA_CATEGORIES`, чипы на `/cinema`,
`/cinema/category/[id]`) удалены — на смену им пришёл единый каталог с
чипами жанров (AND/exclude) и сортировкой, общий по устройству с каталогом
аниме. Полное описание — §15 («Навигация и каталог»), TMDB-рейтинг для
«Популярного» кино — §15.3.

## 8. Уведомления о новых сериях

Крон `src/app/api/cron/check-episodes/route.ts`, расписание в `vercel.json`
(`0 6 * * *`, раз в сутки — сознательно, из-за ограничения частоты крона на
Vercel Hobby-тарифе).

Логика: для каждого уникального тайтла в статусе `watching` у кого-либо —
текущее число серий (`getAnime`+`episodeCount` для аниме, `getCinemaById`
для кино — переиспользование существующих функций каталогов, новых внешних
интеграций не потребовалось) сравнивается с `title_episode_baseline`. При
росте — уведомление **всем**, кто смотрит этот тайтл (не только тому, кто
инициировал проверку). Первая встреча тайтла — молчаливый посев baseline,
без уведомления (иначе старые серии считались бы «новыми» задним числом).

Защита эндпоинта — заголовок `Authorization: Bearer $CRON_SECRET` (Vercel
сам его добавляет к cron-запросам, если задать `CRON_SECRET` в env).

Требует `SUPABASE_SERVICE_ROLE_KEY` (`src/lib/supabase/service.ts`) — крону
нужно читать `user_list` **всех** пользователей, обычный клиент под RLS
этого не может.

`NotificationBell.tsx` в шапке — initial-список сервером (Navbar уже async
Server Component), дальше Realtime-подписка на `INSERT`. Mark read —
напрямую с клиента (`supabase.from('episode_notifications').update()`,
работает под RLS, без отдельного API route).

### 8.1. Системные уведомления (только админам)

Отдельная таблица `system_notifications` (миграция `0006`, НЕ трогает схему
`episode_notifications`) — под уведомления не про серии, а про
инфраструктуру: например, истечение пробного периода видеобалансера.
Видны только `ADMIN_EMAILS` (`src/lib/admin.ts`) — RLS ограничивает
`user_id`, поэтому у обычного пользователя строк там просто нет, отдельно
фильтровать не нужно ни в `Navbar.tsx`, ни в кроне.

`NotificationBell.tsx` объединяет `episode_notifications` и
`system_notifications` в один список (`AppNotification` — discriminated
union по `kind`, см. `lib/types.ts`), рендерит по-разному (у системных нет
постера/ссылки на тайтл, свой текст), realtime-подписка на `INSERT` в обеих
таблицах отдельно.

**Vibix trial** (`src/lib/vibixTrial.ts`) — первый и пока единственный
источник системных уведомлений. Пробный период 17.07.2026–17.10.2026 (даты
захардкожены, не из API — это бизнес-факт, а не то, что можно узнать у
Vibix программно). Три вехи (месяц/2 недели/неделя до конца) проверяются
внутри уже существующего суточного крона `check-episodes` (без отдельной
записи в `vercel.json` — Vercel Hobby и так ограничивает число cron job'ов).
Админов ищем через `supabase.auth.admin.listUsers()` (service_role) и
фильтр по email — `auth.users` не читается напрямую через `.from()`.
Идемпотентность — `unique(user_id, key)` + `upsert(..., ignoreDuplicates:
true)`: проверяются ВСЕ вехи, чей срок уже настал (не только «сегодня
ровно»), поэтому пропущенный суточный прогон не теряет уведомление, а не
шлёт его повторно, если уже отправлено.

Тот же статус (дней до конца) продублирован в `/profile` —
`VibixTrialStatus.tsx`, видна только админам, без похода в уведомления.

## 9. Известные ограничения / технический долг

- **`src/lib/kodik-catalog.ts` — мёртвый код.** Каталог кино переехал на
  Videoseed (у него в разы больше сериалов), этот файл больше нигде не
  импортируется. Можно удалить.
- **Позиция на Videoseed — оценка, не факт.** См. §7. Пользователь может
  дождаться ответа их поддержки — тогда оценщик заменяется точными событиями.
- **Alloha/Sibnet/Aksor (через Yummy) — трекинг невозможен.** Подтверждено
  экспериментально для Alloha (нет postMessage в принципе), для Sibnet/Aksor
  не проверялось (малая доля выдачи, ~10% и ~5% соответственно).
- **Кросс-источниковый перенос позиции неполный.** Для аниме `HlsPlayer` ↔
  `KodikPlayer` переносят живую позицию через `bumpPosition`/`livePositionRef`
  при ручном переключении внутри сессии. `YummyPlayer` в этот перенос не
  включён — только резюм из БД при новой загрузке страницы.
- **Собственный плеер (§12) резолвит только Alloha и Videoseed.** AniLibria
  уже отдаёт прямой HLS в браузер (§6) — отдельный прокси ему не нужен.
  Kodik/Vibix/Sibnet/Aksor через прокси не пропускаются намеренно: у них нет
  известного стабильного паттерна перехвата, как у Alloha/Videoseed.
- **Puppeteer-резолв — самая долгая часть первого запроса серии** (секунды,
  холодный кэш `resolved_streams`). Пока это не оптимизировано (нет
  предзагрузки/варминга при заходе на страницу тайтла) — см. §12.2.
- **Vercel Hobby-тариф ограничивает крон** раз в сутки — если тариф сменится
  на Pro, можно увеличить частоту проверки новых серий.

## 12. Собственный плеер — прокси-стриминг

### 12.1. Общая архитектура

Никакого VPS и никакого Telegram — видео идёт напрямую с сайта, целиком на
Vercel serverless-функциях. Идея: тот же приём, которым раньше извлекали
видео для скачивания (Puppeteer-перехват сети в эмбед-плеере источника),
только результат не скачивается на диск и не пересылается — сервер сразу
проксирует байты Range-кусками в `<video>` на странице.

```
Браузер                    Vercel (serverless)                  Апстрим
┌──────────────┐          ┌────────────────────────────┐       ┌──────────┐
│ <video src=  │  Range   │ /api/proxy/.../[source]     │       │ Alloha / │
│  /api/proxy> │ ───────→ │  1. resolveStream()         │       │ Videoseed│
│              │          │     — кэш в resolved_streams│       │ (embed-  │
│  hls.js для  │          │     — при промахе: Puppeteer│──────→│ плеер)   │
│  HLS-плейлис-│          │       (@sparticuz/chromium) │       └──────────┘
│  тов         │          │       перехватывает .mp4/   │
│              │ ←─────── │       .m3u8 у эмбеда         │
└──────────────┘  байты   │  2. fetchAndProxy() —        │
                          │     Range-пересылка байт     │
                          └────────────────────────────┘
```

Ничего не хранится дольше кэша ссылки (§12.2) — ни на Vercel (serverless,
без диска между вызовами), ни где-либо ещё.

### 12.2. Резолв прямой ссылки и кэш

`src/lib/extract/resolve.ts` — единая точка входа:

1. Ищет в Supabase (`resolved_streams`, только `service_role`) свежую запись
   `(content_type, shikimori_id, season, episode, source)`.
2. Если есть и не истекла (`expires_at`) — возвращает её сразу, без Puppeteer.
3. Иначе запускает экстрактор источника (§12.3), сохраняет результат с
   TTL **15 минут** и возвращает его.

TTL короткий специально: апстрим-ссылки Alloha/Videoseed — подписанные и
недолговечные (как раньше для скачивания). Если TTL истёк посреди
просмотра — следующий Range-запрос сам перерезолвит ссылку (секунда-две
паузы, плеер это переживает как обычную буферизацию); отдельного механизма
предзагрузки/варминга пока нет (см. §9).

### 12.3. Извлечение и проксирование по источникам

#### Alloha (`src/lib/extract/alloha.ts`)
YummyAnime API → `iframe_url` Alloha-эмбеда → headless Chromium (Referer:
`yani.tv`) → перехват сетевых запросов, ищем `.mp4`/`.m3u8`.

#### Videoseed (`src/lib/extract/videoseed.ts`)
`buildEmbedUrl(kpId, token, season, episode)` → headless Chromium (Referer:
`videoseed_host`) → перехват `.mp4`/`.m3u8`.

Оба перехватчика — Puppeteer поверх `puppeteer-core` + `@sparticuz/chromium`
(`src/lib/extract/browser.ts`): сжатый бинарник Chromium распаковывается в
`/tmp` внутри serverless-функции при первом запуске, отдельного контейнера/
VPS не требуется. Флаги запуска (`--single-process --no-zygote`) — то же
самое, чем раньше ужимали Puppeteer под 1 ГБ RAM VPS, здесь просто экономят
память лимита функции.

#### Проксирование (`src/lib/extract/proxy.ts`, `fetchAndProxy`)
- **Прямой mp4**: входящий `Range` заголовок пересылается апстриму как есть
  (плюс `Referer` из результата резолва), ответ (206/200 + заголовки)
  транслируется в браузер потоково, без буферизации на сервере.
- **HLS (m3u8)**: плейлист скачивается и переписывается — каждая ссылка на
  сегмент/суб-плейлист/ключ (`URI="..."`) заменяется на подписанный
  `/api/proxy/raw?u=...&s=...` (см. ниже), чтобы hls.js в браузере ходил
  только на наш домен, а не напрямую на CDN источника (у которого хотлинк-
  защита по Referer, недоступному из браузера пользователя).

#### `/api/proxy/raw` — подписанные сегменты
`u` — `base64url(JSON{url, headers, exp})`, `s` — `HMAC-SHA256(u, PROXY_SIGNING_SECRET)`.
Без верной подписи — 403: иначе эндпоинт превратился бы в открытый
прокси-редирект на произвольные URL (SSRF). Токен живёт 6 часов — с запасом
на любой сеанс просмотра.

### 12.4. Собственный плеер (`OwnPlayer.tsx`)

Не iframe, а полноценный `<video>` со своими контролами (не нативные
`<video controls>` — так кнопки пропуска опенинга/титров и переход на
следующую серию видны и в полноэкранном режиме, который берётся на весь
контейнер, а не на сам `<video>`):

- При смене серии — `HEAD` на `/api/proxy/...`, по `Content-Type` ответа
  определяется HLS это или mp4 → дальше либо `hls.js` (динамический импорт,
  как в `HlsPlayer.tsx`), либо просто `video.src`.
- Резюм позиции — `seekTargetRef`, применяется на `loadedmetadata`.
- Пропуск опенинга/эндинга — те же тайминги, что и у HLS-плеера (YummyAnime,
  §6), кнопка показывается по `timeupdate`.
- Прогресс просмотра — общий `useProgressSaver` (тот же хук, что у
  `HlsPlayer`), с добавленным полем `season` (кино может быть многосезонным).
- Ошибки апстрима (`404` — серии нет у источника, `502` — Puppeteer/сеть
  подвели) показывают разные состояния: «недоступно» без кнопки повтора vs
  «не удалось загрузить» с кнопкой «Повторить».

Подключается как ещё один пункт переключателя источника — «Наш плеер»:
в `WatchPlayer.tsx` (аниме) при доступной Alloha (через Yummy), в
`Player.tsx` (кино) при доступном `VIDEOSEED_TOKEN`.

### 12.5. Известные компромиссы

- Первый запрос серии после истечения TTL — самый долгий (Puppeteer, секунды
  холодного старта headless Chromium + перехват сети). Кэш сглаживает это
  для всех, кто смотрит эту же серию в ближайшие 15 минут.
- `resolveStream` не защищён от одновременного дублирующего резолва двумя
  параллельными Range-запросами одной и той же ещё не закэшированной серии
  (гонка `upsert` в `resolved_streams` — не страшно, оба запроса просто
  получат рабочую ссылку, лишний Puppeteer-запуск не критичен).
- **Alloha требует Referer у самого top-level запроса навигации** —
  `page.setExtraHTTPHeaders({ Referer })` в Puppeteer НЕ гарантированно
  применяется к главному документу (только к подресурсам); без него Alloha
  сразу отдаёт HTTP 404 «Ошибка!». Решается через опцию `page.goto(url, {
  referer })` — уходит напрямую в CDP `Page.navigate`. Подтверждено
  вручную через реальный браузер (открыть yani.tv → перейти по ссылке на
  alloha.yani.tv из него — 200; открыть ссылку напрямую без Referer — 404).
- **У Alloha ДВЕ разные защиты, легко перепутать одну с другой.**
  1. **Анти-хотлинк на уровне фронтенда страницы-эмбеда** — скрипт
     проверяет `window !== window.top` (открыта ли страница именно ВНУТРИ
     `<iframe>`, как в реальном использовании на yani.tv) и, если нет,
     СТИРАЕТ `<body>`, подставляя текст «Контент не найден или недоступен
     в вашем регионе». Это сработало на ЛЮБОМ IP (не только RU) при обычном
     `page.goto(embedUrl)` — потому что Puppeteer открывает URL как
     top-level документ. Текст сообщения маскирует эту проверку под
     гео-блок, но реальной проверки IP/страны здесь нет вообще.

     Обход в `interceptVideoUrl` (`alloha.ts`): вместо `page.goto(embedUrl)`
     переходим на фиктивный `WRAPPER_URL` (реальный домен `yani.tv/...` —
     важен для правдоподобного Referer) — сам запрос никогда не уходит в
     сеть, перехватывается через `request.respond()` и наполняется HTML с
     `<iframe src="embedUrl">`. Внутри iframe `window !== window.top` —
     проверка проходит, страница не стирает себя. Referer у собственной
     навигации iframe браузер выставляет сам (наследует URL родителя).
  2. **Настоящий гео-блок — на бэкенд-эндпоинте `/bnsi/movies/{id}`**,
     который резолвит реальный файл по id уже ПОСЛЕ того, как страница
     отрендерилась (п.1 выше пройден). Подтверждено экспериментально:
     один и тот же embed, один и тот же id, с IP датацентра — 404
     `{"error":"контент не найден"}` (тот же generic-текст, что и у
     проверки isFramed, тоже маскирует реальную причину), а с обычного
     российского IP тот же запрос отдаёт данные, ведущие дальше к
     настоящему `master.m3u8` на `*.vkvideo.cloud`. Разница — только в
     исходящем IP запроса, всё остальное идентично.

  Дополнительно приходится отфильтровывать `cdn.plyr.io/static/blank.mp4`
  (`DECOY_HOSTS`) — служебная заглушка библиотеки плеера Plyr, которую он
  грузит перед реальным источником; без фильтра по приоритету
  `mp4 || m3u8` код бы хватал именно её.
- **RU-прокси нужен по-настоящему — но только для запроса №2 выше**, и
  подключается нетривиально. Присланный пользователем HTTP(S)-порт прокси
  (1191) на практике не отвечал вообще (curl зависал без ответа);
  рабочим оказался только SOCKS5-порт (11191, подтверждён `curl -x
  socks5h://...` → реальный IP из Москвы). А Chromium не умеет
  авторизованный прокси НАПРЯМУЮ ни для одного протокола: HTTP(S) с
  паролем требует отдельного CDP-запроса `page.authenticate()` (что и
  так неприменимо — тот порт не отвечал), а авторизованный SOCKS5 не
  поддержан НИКАК — `--proxy-server=socks5://user:pass@host` Chromium
  просто не распарсит.

  Решение — пакет `proxy-chain` (`resolveProxy()` в `browser.ts`):
  поднимает локальный анонимный HTTP-прокси на `127.0.0.1`, который сам
  форвардит на настоящий SOCKS5-апстрим с логином/паролем (используя
  `socks-proxy-agent` под капотом) — Chromium подключается к этому
  локальному мосту через `--proxy-server` вообще без авторизации.
  `ALLOHA_PROXY_SERVER` в `.env.example` — SOCKS5-адрес (`socks5://host:
  port`), не HTTP(S).

  ⚠️ **Открытый вопрос, не проверенный на момент записи**: проксируется
  только само извлечение (`launchBrowser` в `extractAlloha`) — Puppeteer
  ходит на страницу-эмбед и на `/bnsi/`. Реальный CDN с видео
  (`*.vkvideo.cloud`), который потом читает `fetchAndProxy` в `proxy.ts`
  (уже НЕ через Puppeteer, обычный серверный `fetch()`), проксироваться
  не будет — если он тоже проверяет IP отдельно от `/bnsi/`, воспроизведение
  всё ещё будет падать уже на этапе стриминга байт, и это придётся
  проксировать отдельно (счёт трафика будет уже в гигабайтах на серию, а
  не в килобайтах, как на этапе резолва).

/catalog?genres=&exclude=&sort=&page=       — каталог аниме: жанры (AND/exclude) + сортировка (§15)

/cinema/popular?page=N                      — «Популярное» кино (TMDB-рейтинг на весь пул), пагинация
/cinema/new?page=N                          — «Новинки» кино (сортировка по году), пагинация
/cinema/catalog?genres=&exclude=&sort=&page= — каталог кино: жанры (AND/exclude) + сортировка (§15)
/cinema/[id]                               — страница тайтла кино (id = kinopoisk_id)
/cinema/watch/[id]/[season]/[episode]      — просмотр кино

## 14. Доступ к сайту — регистрация по коду, полный auth-gate

Сайт полностью закрыт для незарегистрированных — продуктовое решение, не
техническое ограничение. Раньше каталог/просмотр были публичными, вход
требовался только для `/profile`; теперь `updateSession()`
(`src/lib/supabase/middleware.ts`) инвертирован на allowlist: без сессии
доступны только `/login` и `/signup`, всё остальное (включая `/`, каталоги,
просмотр, `/code`) редиректит на `/login?redirect=...`. Роуты `/api/*` из
этого редиректа исключены намеренно — они либо сами проверяют `user` и
отдают 401 JSON (редирект на HTML сломал бы fetch-клиентов), либо обязаны
быть доступны анониму по своей природе (`/api/signup`, `/api/login`).

**Существующие сессии не задеты** — гейт проверяет ровно то же
`supabase.auth.getUser()`, что и раньше, просто в других условиях; уже
залогиненные пользователи проходят как проходили, никакой миграции данных
не потребовалось (новых обязательных полей в БД нет).

### 14.1. Код приглашения

Регистрация требует 20-символьный код (`src/lib/signupCode.ts`), который
**не хранится нигде** — детерминированно выводится из
`HMAC-SHA256(SIGNUP_CODE_SECRET, дата_UTC)`, отображённого в алфавит без
визуально спутываемых символов (без `0/O`, `1/I/L`). Код автоматически
меняется в полночь UTC — не нужны ни таблица в БД, ни крон на ротацию, код
на `/api/signup` и на `/code` всегда совпадает, потому что считается
одинаково. Без `SIGNUP_CODE_SECRET` в окружении — регистрация закрыта для
всех (fail closed).

`/code` (`src/app/code/page.tsx`) показывает код на сегодня, но только
аккаунту `2000gva@gmail.com` (хардкод в файле) — остальным, включая других
авторизованных пользователей, отдаётся `notFound()`, чтобы не подтверждать
даже сам факт существования страницы.

### 14.2. Регистрация и вход — только через свои Route Handlers

`POST /api/signup` и `POST /api/login` — сознательно НЕ прямые вызовы
`supabase.auth.signUp()`/`signInWithPassword()` с клиента (как было раньше в
`AuthForm.tsx`). Причина: `NEXT_PUBLIC_SUPABASE_ANON_KEY` публичный по
дизайну — если бы код приглашения проверялся только в браузере, кто угодно
вызвал бы Supabase Auth API напрямую из консоли, в обход проверки.

`/api/signup` создаёт пользователя через `service_role`
(`auth.admin.createUser`, `email_confirm: true` — код приглашения уже
достаточное подтверждение) и сразу логинит через cookie-aware клиент.

⚠️ **Это даёт защиту только на уровне нашего кода.** Чтобы закрыть путь
полностью, в Supabase Dashboard → Authentication → Settings нужно ОТКЛЮЧИТЬ
«Allow new users to sign up» — иначе обычный `supabase.auth.signUp()`
всё ещё физически доступен напрямую через публичный anon key, в обход
`/api/signup` и его проверки кода. Это ручной шаг, который нельзя
выполнить из кода репозитория.

### 14.3. Rate limiting

`src/lib/rateLimit.ts` — in-memory sliding window по IP, общий для
`/api/signup` и `/api/login`: **5 запросов/мин**. Best-effort компромисс
serverless Vercel — живёт в рамках одного тёплого инстанса функции, не
строгая гарантия между инстансами/после cold start, но первая линия защиты
от перебора. `AuthForm` показывает оставшиеся попытки (`remaining` в ответе
роута) прямо в форме.

## 15. Навигация и каталог (аниме + кино)

Единая структура для обоих разделов: главная — «Продолжить просмотр» +
3 плитки (`NavTile.tsx`) → **Популярное** / **Новинки** / **Каталог**.
Раньше жанры выбирались чипами прямо на главной (аниме) и вкладками
категорий (кино, `CINEMA_CATEGORIES` — удалено); теперь это единственная
задача **Каталога** — на главной жанровых чипов больше нет вообще.

### 15.1. Множественный выбор, исключение, AND — ограничения API

Ни у Shikimori, ни у Videoseed НЕТ на уровне API ни AND-комбинирования
жанров, ни исключения — проверено вживую:

- `genre=1,4` у Shikimori (REST и GraphQL — те же аргументы у резолвера) —
  это **OR**, не AND. `genre=1,-4` не исключает 4-й жанр — любой
  нераспознанный токен в списке просто обнуляет результат в `[]`.
- У списковых ответов Shikimori (`/animes`) вообще НЕТ жанров по тайтлу —
  только у полной карточки (`/animes/{id}`). У Videoseed жанр — обычное
  текстовое поле прямо в каждой записи списка (дешевле).

Поэтому AND/exclude реализованы целиком на нашей стороне, с разной ценой:

- **Кино** (`getCinemaCatalog` в `videoseed-catalog.ts`) — дёшево: жанр уже
  под рукой в списке, `matchesFilter()` — просто проверка подстрок.
- **Аниме** (`getAnimeCatalog` в `shikimori.ts`) — дороже: include-жанры
  используются как OR-предфильтр (сужает пространство поиска, хоть и не
  даёт точный AND), затем на каждого кандидата параллельно (см.
  `mapWithConcurrency`, `src/lib/concurrency.ts`, окно в 5) догружается
  полная карточка и проверяется реальный список жанров. «Быстрый путь» без
  этой догрузки — только когда нет exclude и максимум один include-жанр
  (`genre=X` и так точный OR из одного элемента).

Кэш `getAnime()` (час) делает повторные заходы по той же комбинации почти
бесплатными — цена AND/exclude платится один раз «в фоне» первым, кто
открыл редкую комбинацию, а не каждым посетителем.

### 15.2. Потолок против таймаута

У serverless-функций Vercel есть жёсткий лимит времени выполнения —
`/catalog` и `/cinema/catalog` объявляют `export const maxDuration = 60`
(как и у крона уведомлений). `MAX_CATALOG_CANDIDATES = 120` в
`shikimori.ts` — потолок карточек, которые аниме-каталог готов догрузить за
один запрос: при троттлере 5 rps это ~24 сек, с запасом от лимита
Shikimori 90 rpm (сознательно НЕ близко к 90 — на сервере может быть
несколько одновременных заходов в каталог). У кино-каталога аналогичная
роль у `MAX_UPSTREAM_PAGES = 30` (страниц апстрима, не карточек — жанр не
требует догрузки). На редкой комбинации потолок может отдать чуть меньше
результатов, чем реально существует в каталоге, — это осознанный компромисс
(не упасть по таймауту важнее полноты редкого запроса).

### 15.3. «Популярное» кино — TMDB на весь пул

У Videoseed нет рейтинга/популярности вообще, ни для одной записи.
`getPopularCinemaRanked()` сортирует весь пул кандидатов по TMDB
`vote_average` (через `id_imdb`, см. `lib/tmdb.ts`) — не только «Зарубежные
сериалы»/«Русские сериалы», как было раньше в `CINEMA_CATEGORIES`, а вообще
все фильмы и сериалы. Без `TMDB_API_KEY` сортировка no-op (порядок как
пришёл от Videoseed).

«Новинки» кино (`getNewCinema()`) сортируются по году — точной даты выхода
у Videoseed нет, только год.

### 15.4. `GenreFilterPanel` — общий компонент

`src/components/GenreFilterPanel.tsx` — один клиентский компонент для
каталога аниме и кино. Не держит состояние в React — читает/пишет ТОЛЬКО
URL searchParams (`genres`, `exclude`, `sort`), поэтому «сохранение
фильтров при возврате назад» получается само собой (обычная навигация
браузера). Каждый жанр-чип — 3 состояния по клику: нейтрально → включить →
исключить → нейтрально. Значения жанров разные по смыслу у разделов
(числовой id Shikimori у аниме, название текстом у кино), но общий по
форме `{ value, label }[]`, так что компонент один.

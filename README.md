# MediaWatch — аниме, фильмы и сериалы с кросс-девайс синхронизацией

Веб-приложение для просмотра аниме и фильмов/сериалов из открытых источников.
Главная фича: позиция просмотра (**тайтл → сезон → серия → секунда**)
сохраняется в облаке и автоматически восстанавливается на любом устройстве
после входа в аккаунт.

Сайт сам не хостит видео — встраивает сторонние видеобалансеры либо
проксирует поток через собственный плеер (см. ниже).

## Что изменилось с 8 сентября

Сводка по 62 коммитам (08.09 23:44 — 10.09 02:36 МСК, 103 файла). Подробности
каждой правки — в её коммите и в комментариях к коду.

### Каталоги перевели на свой индекс

Раньше фильтрация шла запросами к чужим API. Теперь у обоих каталогов —
собственная копия в Supabase, перестраиваемая ночью, и один SQL-запрос вместо
десятков внешних.

- **Аниме**: локальный индекс (`anime_index`), фильтры по типу, статусу,
  жанрам, годам, сериям и рейтингу, трёхпозиционные галки «включить /
  исключить».
- **Кино**: то же самое с нуля — 93 529 тайтлов, жанры, тип (сериал, фильм,
  мультсериал, мультфильм, короткометражка), страна, год; сортировки по
  новизне, дате последней серии, популярности, рейтингу и алфавиту.
  Индексация занимает ~7 минут и около 4% суточной квоты Videoseed.
- **Рейтинги TMDB** для кино — отдельной таблицей и своим недельным кроном,
  со сглаживанием по числу голосов: «10.0 от двух зрителей» больше не
  обгоняет всё остальное.
- **Поиск** — на триграммах прямо по индексу, с ранжированием: точное
  совпадение → начало строки → вхождение → похожесть, дальше по
  популярности.
- Панель фильтров, вид сеткой и списком, дропдаун сортировки со значком
  текущего порядка — общие для обоих каталогов (`src/lib/catalogFilters.ts`).

### Обложки — свои, с диска

Постеры приходили из трёх чужих мест, каждое со своей задержкой и своей
точкой отказа. Теперь 112 893 файла лежат у нас (2,5 ГБ) и отдаются nginx.

Замерено на проде: **24 мс против 3127 мс** у тех же картинок через
Videoseed. Пока файла нет, карточка сама берёт прежнюю ссылку на апстрим —
незакэшированный тайтл выглядит как раньше, а не ломается.

### Плеер

- **Субтитры — отдельной кнопкой** со значком «CC» слева от настроек: список
  дорожек и оформление (цвет текста, размер, прозрачность текста, обводка,
  цвет и прозрачность фона, сброс). Рисуем их сами, над панелью управления,
  чтобы не заходили под неё.
- **Выбор переживает смену серии**: озвучка, субтитры и доп. аудиодорожка
  запоминаются подписью (идентификаторы у каждой серии свои). Не нашлось —
  предупреждение и доступный вариант.
- **Alloha восстановлена.** Их CDN начал требовать пару заголовков подписи
  (`authorizations` / `accepts-controls`) — без них 403 получали все: наш
  сервер, посторонний IP и настоящий Chrome. Экстрактор снимает их с
  запросов плеера, прокси перестал их терять (у `node-wreq` стоял флаг,
  подставлявший собственные заголовки вместо переданных).
- **Протухшая ссылка больше не тупик.** Раньше мастер-плейлист отдавался из
  нашего 15-минутного кэша с кодом 200, а подписанные ссылки внутри у CDN
  уже не работали: плеер выглядел рабочим, но не играл, и обновление
  страницы давало тот же кэш. Теперь клиент замечает пачку неудачных
  загрузок (hls.js такие ошибки считает нефатальными и перебирает варианты
  бесконечно) и просит переизвлечь ссылку заново.
- **Битое сочетание «серия × озвучка»** — переход на соседнюю озвучку, по
  возможности ту же студию у другого источника. Решение принимает родитель,
  единственный владелец состояния: версия, где это делал сам плеер,
  зацикливалась и роняла страницу.
- У Alloha появился выбор качества (каждое живёт по своей ссылке, поэтому
  переключение — полной заменой источника). Real-Debrid скрыт из выбора.

### Интерфейс

- Нижняя док-панель на телефоне: каталог — логотип — профиль, поиск наверху
  получил освободившееся место.
- Полупрозрачное «стекло» у шапки, уведомлений, поиска и дропдаунов. Чинили
  дважды: панели выносятся порталом в `body` (внутри шапки они размывали её,
  а не страницу), и с них убрана анимация прозрачности — завершённая
  анимация с `fill: both` остаётся на элементе навсегда, и Chrome на этом
  непредсказуемо выбрасывал размытие.
- Переключатель «Аниме / Фильмы» на главной и в профиле — переезжающим
  ползунком (`useSlidingPill`), а не мигающей заливкой.
- Скелетоны, выравнивание каруселей по колонке каталога, крестик удаления в
  уведомлениях, ширина и высота у картинок.

### Эксплуатация

- **Деплой больше не роняет прод** — сборка в сторону, атомарное
  переключение, автооткат. Подробности и грабли — в разделе «Деплой».
- **Страница `/admin/status`**: состояние индексов, рейтингов и кэша
  обложек, ошибки последних прогонов и **кнопки ручного запуска** задач.
  Запуск идёт тем же путём, что системный крон, не светя `CRON_SECRET` в
  браузер.
- Ротация секретов: `CRON_SECRET` читается кроном из `.env` в момент
  запуска, а не зашит в строку расписания.

## Стек

- **Next.js 14** (App Router, Server Components) + **TypeScript** + **Tailwind CSS**
- **Supabase** — Postgres + Auth + Row Level Security + Realtime
- **Самостоятельный хостинг на VPS** — standalone-сборка Next.js под PM2
  (`output: 'standalone'` в `next.config.js`, деплой — `scripts/deploy.sh`)
- **Capacitor 8** — iOS-обёртка (`ios/`, `capacitor.config.ts`, сборка в `codemagic.yaml`)
- **Sentry** — мониторинг ошибок (опционально)
- Воспроизведение: **hls.js** / **dashjs**
- Метаданные: **Shikimori** (аниме), **TMDB** и **Videoseed API v2** (кино)
- Балансеры/плееры: **Kodik**, **Videoseed**, **Vibix**, **AniLibria**,
  **YummyAnime**, **Alloha**

Вся серверная логика сайта — Next.js Route Handlers / Server Components +
Supabase, отдельного бэкенда нет. Рядом на VPS живёт независимый сервис
`vps-extractor/` (см. «Собственный плеер»).

Требуется **Node 22.x** (см. `engines` в `package.json`).

## Быстрый старт локально

```bash
npm install
cp .env.example .env.local   # заполните значениями (см. ниже)
npm run dev                  # http://localhost:3000
```

## 1. Проект Supabase

1. Создайте проект на <https://supabase.com> (бесплатный тариф).
2. **Project Settings → API** → скопируйте:
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon` `public` ключ → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `service_role` ключ → `SUPABASE_SERVICE_ROLE_KEY` (секретный, нужен
     регистрации и крону)
3. **Authentication → Providers → Email**: включите Email. Для локальной
   разработки удобно отключить `Confirm email` (тогда вход сразу после
   регистрации); в проде оставьте подтверждение включённым.

## 2. Применение SQL-миграций

Откройте **SQL Editor** в Supabase и выполните файлы из
[`supabase/migrations/`](supabase/migrations/) **по порядку номеров**
(`0001_init.sql` … `0034_search_functions.sql`) — одной первой миграции
недостаточно, схема набиралась инкрементально.

`0001_init.sql` создаёт таблицы `watch_progress` и `user_list`, включает RLS с
политиками «пользователь видит только свои строки» и добавляет
`watch_progress` в публикацию Realtime. Дальше добавляются
`watched_episodes`, `episode_notifications`, `title_episode_baseline`,
`system_notifications`, `resolved_streams`, `subtitle_cache`, `app_settings`,
`api_response_cache`, `user_presence`, `user_theme`, `anime_index`,
`cinema_index`, `cinema_ratings`, `poster_cache` и правки к ним.

> Через Supabase CLI: `supabase db push` (после `supabase link`).

На проде Supabase самохостится в докере, поэтому миграция применяется так:
файл копируется внутрь контейнера (`docker cp … supabase-db:/tmp/`) и
выполняется там же:

```bash
docker exec -i supabase-db psql -U postgres -d postgres -f /tmp/00NN_….sql
```

`SUPABASE_DB_URL` в серверном `.env` для этого НЕ годится: там остался адрес
облачного Supabase, которого давно нет (`psql` по нему падает с
`tenant/user … not found`). Сервисный ключ через PostgREST DDL тоже не
выполняет — через него миграцию не применить.

## 3. Kodik-токен (опционально)

Токен Kodik бесплатный, но выдаётся по запросу
(<https://kodik.cc/> → раздел для разработчиков / поддержка).

- **Режим A (есть токен):** укажите `KODIK_TOKEN` в окружении — сервер
  проксирует поиск плеера (`/api/kodik`), становятся доступны выбор озвучки и
  список серий. Тот же токен используется как один из каталогов раздела
  «Фильмы и сериалы».
- **Режим B (нет токена):** приложение автоматически использует публичный
  `find-player`-iframe как fallback. Часть событий плеера и селектор озвучки
  могут быть недоступны.

Вкладка «Kodik» убрана из переключателя плеера по умолчанию и остаётся
запасным вариантом, если ничего другого не резолвнулось. Вернуть её как
обычную вкладку можно живым флагом в профиле (админ, без редеплоя — см.
`src/components/KodikPlayerToggle.tsx`, `src/lib/settings.ts`, миграция 0013).

Источник видео абстрагирован интерфейсом `VideoSource`
([`src/lib/video/types.ts`](src/lib/video/types.ts)) — замена провайдера не
затрагивает остальное приложение.

## Собственный плеер

«Наш плеер» стримит видео напрямую с сайта: прямая ссылка у эмбед-плеера
источника (Alloha/Videoseed и др.) извлекается **отдельным VPS-сервисом**
([`vps-extractor/`](vps-extractor/README.md) — обычный Puppeteer на VPS),
результат кэшируется в `resolved_streams` на 15 минут, а приложение проксирует
байты Range-кусками в `<video>`.

Серверное извлечение внутри Vercel serverless (`@sparticuz/chromium`) и
вариант с клиентским зеркалом эмбеда антибот источников не проходят — обе
попытки сняты, история в `ARCHITECTURE.md` §12.5–12.6.

Нужны `PROXY_SIGNING_SECRET` (подпись внутренних URL сегментов HLS — без него
`/api/proxy/raw` отклоняет все запросы, чтобы не стать открытым SSRF-прокси) и
`VPS_EXTRACTOR_URL` / `VPS_EXTRACTOR_TOKEN`. Подробности — `ARCHITECTURE.md` §12.

Что умеет: выбор качества (у Alloha и Aksor — полной заменой источника, у них
каждое качество живёт по своей ссылке), доп. аудиодорожки, субтитры отдельной
кнопкой «CC» с настройкой оформления, пропуск заставки и титров, картинка в
картинке, продолжение серии без перезагрузки страницы. Выбор озвучки,
субтитров и аудиодорожки запоминается **подписью** и переживает смену серии:
идентификаторы дорожек у каждой серии свои, а подпись стабильна.

Живучесть потока (всё воспроизведено на проде и описано в комментариях к
`OwnPlayer.tsx` / `lib/extract/proxy.ts`):

- Ссылки апстрима живут КОРОЧЕ нашего 15-минутного кэша. Тогда мастер-плейлист
  отдаётся из кэша с кодом 200, а подписанные ссылки внутри уже мертвы — плеер
  выглядит рабочим, но не играет, и обновление страницы даёт тот же кэш.
  Клиент замечает пачку неудачных загрузок и просит переизвлечь (`?fresh=1`).
  Ждать фатальной ошибки от hls.js бесполезно: ошибки загрузки вариантов он
  считает нефатальными и перебирает их бесконечно.
- Если у источника битым оказалось одно сочетание «серия × озвучка», плеер
  переходит на соседнюю озвучку — по возможности ту же студию у другого
  источника — и предупреждает. Решение принимает родительский компонент,
  единственный владелец состояния: версия, где это делал сам плеер,
  зацикливалась.
- CDN Alloha (`vkvideo.cloud`) требует пару заголовков подписи
  (`authorizations` / `accepts-controls`) — без них 403 получают все, включая
  настоящий браузер. Экстрактор снимает их с запросов плеера и отдаёт вместе
  со ссылкой. Отдельно важно: у `node-wreq` (подмена TLS-отпечатка для этого
  же CDN) флаг `browser.headers` должен быть `false`, иначе он подставляет
  свои заголовки **вместо** переданных.

## 5. Деплой

CI/CD нет: пуш в `origin/main` сам по себе сайт **не** обновляет. Деплой —
вручную по SSH на продакшен-VPS, из корня проекта:

```bash
bash scripts/deploy.sh
```

### Как устроен (переделано 10.09.2026)

Сборка идёт **в сторону от живого сайта** и подключается переключением
симлинка:

1. `git pull` → `npm ci`;
2. `npm run build` в НОВЫЙ каталог `.build-<метка>` (через `NEXT_DIST_DIR`,
   см. `next.config.js`) — живой сайт при этом не трогается вовсе;
3. в собранный standalone докладываются `public/`, `static` и нативный
   бинарник `node-wreq` (Next.js в standalone-режиме этого не делает сам —
   без этого шага сайт поднимается, но весь CSS/JS отдаёт 404);
4. симлинк `.current` атомарно переключается на новую сборку, PM2
   перезапускает `mediawatch-web` (он работает из
   `/opt/mediawatch/.current/standalone/server.js`);
5. дым-тест; **при провале — автоматический откат** на прошлую сборку;
6. ротация: остаются три последние сборки.

**Зачем так.** Прежняя схема собирала поверх живого: `next build` первым
делом стирает `.next`, включая `.next/standalone`, из которого работает
сайт. Пока сборка идёт, статика отдаёт 500 — причём HTML продолжает
отвечать 200 с открытых inode'ов процессов PM2 и вводит в заблуждение.
Любое зависание или падение сборки означало сайт без стилей. Так и вышло
09.09: тринадцать минут прод стоял сломанным из-за ошибки типизации,
всплывшей уже после того, как `.next` был стёрт. Теперь неудачная сборка
не доходит до сайта вообще.

### Грабли, на которые здесь наступали

- **Имя каталога сборки обязано быть односегментным** (`.build-<метка>`, а
  не `.releases/<метка>`). В сгенерированных типах страниц Next считает
  глубину `../` исходя из одноуровневого `distDir`, и на двухуровневом
  сборка падает с `Cannot find module ../../../src/app/.../page.js`.
- **`next build` дописывает свой `distDir` в `include` внутри
  `tsconfig.json`.** Строки копятся, старые каталоги удаляются ротацией — и
  следующая сборка падает на тех же `Cannot find module`. Поэтому
  `deploy.sh` возвращает `tsconfig.json` к состоянию репозитория до проверки
  и после сборки. Свои шаблоны вида `.build-*/types/**` в `include`
  добавлять **нельзя** — тот же эффект.
- **Деплой отваливается сразу**, если в рабочем дереве на сервере есть
  незакоммиченные правки отслеживаемых файлов. Чинить
  `git checkout -- <файл>`, не пытаться собрать поверх.

### Осиротевший `.releases` на сервере

До переделки сборки лежали в `/opt/mediawatch/.releases/<метка>`. После
перехода на `.build-*` этот каталог больше не используется и не
ротируется — на проде в нём осталось **около 3,9 ГБ**. Удалять вручную,
когда убедитесь, что откат на старые сборки не понадобится:

```bash
rm -rf /opt/mediawatch/.releases && df -h /
```

Ротация внутри `deploy.sh` его не трогает: она чистит только `.build-*`.

### Прочее

- Переменные окружения — в `.env` на сервере (см. `.env.example`).
  **Важно:** приложение читает не `/opt/mediawatch/.env`, а его копию
  внутри собранного standalone — её кладёт туда `next build`. Правка только
  исходного файла плюс `pm2 restart` не даёт ничего, причём молча. Менять
  надо оба файла либо пересобирать.
- В Supabase **Authentication → URL Configuration** добавьте домен сайта в
  `Site URL` / `Redirect URLs`.
- Расписание фоновых задач живёт в `crontab -l` под root на VPS и в
  `/etc/cron.d/mediawatch-check-episodes` — **в двух местах**, смотреть надо
  оба. `vercel.json` остался со времён Vercel и на VPS ни на что не влияет.
  Состояние всех задач и кнопки ручного запуска — на `/admin/status`
  (только для `ADMIN_EMAILS`).
- `vps-extractor/` разворачивается отдельно — см. его
  [README](vps-extractor/README.md). `deploy.sh` его **не** перезапускает:
  после правок в нём нужно `git pull && pm2 restart mediawatch-extractor`.

## 6. Код регистрации (обязательно)

Сайт закрыт для незарегистрированных полностью — вся регистрация идёт
через один код на сутки, без учётной записи ничего не открыть.

1. Сгенерируйте случайную строку для `SIGNUP_CODE_SECRET`, например:
   `openssl rand -hex 32`.
2. Код на сегодня смотрится на `/code` — доступно ТОЛЬКО одному аккаунту
   (см. `src/app/code/page.tsx`, если email нужно сменить — правьте
   константу там).
3. **Обязательный ручной шаг в Supabase**: Dashboard → Authentication →
   Settings → отключите «Allow new users to sign up». Без этого обычная
   публичная регистрация Supabase всё ещё доступна напрямую через anon key
   в обход кода приглашения — подробности в `ARCHITECTURE.md` §14.2.

## Локальный индекс каталога аниме

Каталог фильтрует не через Shikimori, а по своей копии — таблицы
`anime_index` и `anime_genres` (миграция 0025, чтение —
[`src/lib/animeIndexQuery.ts`](src/lib/animeIndexQuery.ts)). Так фильтр по
жанрам, числу серий, году, рейтингу, типу и статусу становится одним
SQL-запросом.

Зачем: у Shikimori жанров нет в списочном ответе, поэтому AND и исключение
шли догрузкой полных карточек по одной с потолком в 120 штук; фильтра по
числу серий в API v1 нет вовсе; а список жанров из REST `/genres` — легаси
из 46 записей, где «Магия» есть, но не находит ничего (MAL растворил её во
«Фэнтези» и «Махо-сёдзё»). В актуальной таксономии 80 пунктов: 22 жанра,
53 темы, 5 демографий.

Обновление — полная перезакачка с нуля раз в сутки:
`/api/cron/reindex-anime` (заголовок `Authorization: Bearer $CRON_SECRET`),
на сервере в 02:00 UTC, то есть 05:00 по Москве. ~480 страниц по 50 тайтлов
из GraphQL Shikimori, около шести минут; ещё столько же занимает лёгкий
проход за рангами популярности (само поле GraphQL не отдаёт, только
сортировать умеет).

Живая таблица при этом не опустошается: закачка пишет строки со своим
`batch_id`, и указатель `anime_index_state.active_batch` переключается
только после того, как она целиком удалась и прошла проверку на усадку.
Оборвалась — читатели продолжают видеть прошлую партию. Если индекса нет
совсем, каталог откатывается на прежний путь через Shikimori.

### Локальный индекс каталога кино

То же самое для раздела «Фильмы и сериалы» (миграция `0027`,
`lib/cinemaIndex.ts`, чтение — `lib/cinemaIndexQuery.ts`).

Зачем: Videoseed не умеет фильтровать и сортировать ВООБЩЕ — параметры
`year=`, `genre_id=`, `sort_by=` он молча игнорирует (проверено: `total` не
меняется, порядок тот же). Прежний каталог поэтому тянул до 30 его страниц
на каждый клик, отбирал подстрокой по строке жанров (`genre.includes('Драма')`)
и сортировал пул из 120 записей — ни года, ни страны, ни рейтинга по всей
базе, ни честной пагинации так не сделать. Вдобавок это жгло квоту чужого
API на пользовательском трафике.

Обновление — полная перезакачка раз в сутки: `/api/cron/reindex-cinema`,
на сервере в 02:20 UTC (05:20 МСК). 207 запросов по 500 записей (82 455
фильмов + 20 969 сериалов), около семи минут, ~4% суточной квоты Videoseed.
В индекс попадает ~93 тысячи тайтлов: записи без `kinopoisk_id` отсеиваются
(по ним не построить ни плеер, ни прогресс), дубли по нему же схлопываются.

Справочники жанров и стран строятся из самих данных. Сопоставлять id с
названием ПО ПОЗИЦИИ нельзя: названия апстрим отдаёт по алфавиту, id — по
возрастанию, и порядки расходятся (Вестерн=4 идёт раньше Военный=3). Словарь
выводится пересечением множеств по всем записям, выборка набирается отдельно
по фильмам и по сериалам — маркеры «Сериалы»/«Мультсериалы» у фильмов не
встречаются в принципе.

### Локальный кэш обложек

Постеры лежат у нас на диске (`POSTER_DIR`, по умолчанию
`/opt/mediawatch/posters`, по папке на раздел: `anime/`, `cinema/`) и
отдаются nginx напрямую по `/posters/<раздел>/<id>.webp`. Реестр — таблица
`poster_cache` (миграция `0029`), она переживает перестройку индекса:
перекачивать 113 тысяч картинок каждую ночь незачем.

Зачем: обложки приходили из трёх чужих мест, и каждое — своя задержка и своя
точка отказа. Аниме в каталоге — shikimori.io, аниме на главной — yani.tv
(туда подменяются обложки там, где у Shikimori плейсхолдер), кино — через
наш же прокси `/api/proxy/raw`, который на КАЖДЫЙ запрос заново качал
картинку с Videoseed и заново жал её в WebP через sharp, без дискового кэша.

Замерено на сервере: постер аниме 144 КБ оригинал → 47 КБ после сжатия в
WebP шириной 480, постер кино 48 КБ → 18 КБ. Реально скачано 112 893 файла
на 2,5 ГБ (23 781 аниме — 977 МБ, 89 112 кино — 1,5 ГБ), покрытие 99,4% и
95,3%.

Выигрыш замерен на проде уже после перевода главной кино на локальные
обложки: **24 мс** на картинку против **3127 мс** у тех же картинок через
Videoseed.

Докачка: `/api/cron/cache-posters?kind=anime|cinema&limit=N`. За сутки
появляются десятки новых тайтлов, поэтому обычный прогон занимает секунды;
первичный залив гоняется руками кусками через `?limit=`. Пока файла нет,
страница отдаёт прежнюю ссылку на апстрим — карточка пробует ссылки по
очереди (`components/PosterImage.tsx`), так что незакэшированный тайтл
выглядит ровно как раньше, а не ломается.

Рейтинги TMDB живут в отдельной таблице `cinema_ratings`, которая
перестройку переживает, и обновляются своим кроном раз в неделю:
`/api/cron/refresh-cinema-ratings`, воскресенье 01:00 UTC (04:00 МСК).
Причина — TMDB не отдаёт рейтинги пачкой: один запрос на тайтл, 93 тысячи
тайтлов, и всё через VLESS-туннель (`api.themoviedb.org` с VPS заблокирован
по DNS). Прогон ограничен бюджетом запросов (`?limit=`, по умолчанию 40 000),
свежие рейтинги доезжают до выдачи следующей ночью, когда перестройка
скопирует их в партию.

## Оформление

Палитра задана CSS-переменными (`--accent`, `--bg`, `--bg-soft`, `--bg-card`)
с дефолтами в [`globals.css`](src/app/globals.css); `tailwind.config.ts`
ссылается на них, а не хранит цвета. По умолчанию — синий Apple `#2997ff` и
чёрный холст.

Пользователь меняет оформление в **профиле → «Оформление»**: акцент
(произвольный HEX или пресет) и одна из трёх тёмных фоновых тем. Выбор
хранится в таблице `user_theme` (миграция 0024) и подхватывается на других
устройствах; `localStorage` — зеркало, чтобы тема применялась до первой
отрисовки без мигания. Светлой темы нет: интерфейс построен на светлом тексте
поверх тёмного холста. Детали — [`src/lib/theme.ts`](src/lib/theme.ts) и
`ARCHITECTURE.md` §11.

## Как работает синхронизация прогресса

1. Плеер сообщает позицию: Kodik — через `postMessage`
   (`kodik_player_time_update`, `..._pause`, `..._video_ended`; ключи в
   [`kodik-events.ts`](src/lib/video/kodik-events.ts)), собственный плеер и
   HLS — напрямую из событий `<video>`.
2. Клиент ([`Player.tsx`](src/components/Player.tsx),
   [`useProgressSaver.ts`](src/hooks/useProgressSaver.ts)) сохраняет позицию:
   каждые 10 сек во время воспроизведения, при паузе, а также при
   `beforeunload` / `visibilitychange(hidden)` — через
   `navigator.sendBeacon('/api/progress')`, чтобы флаш не терялся при закрытии
   вкладки.
3. Route Handler [`/api/progress`](src/app/api/progress/route.ts) делает upsert
   в `watch_progress` по `(user_id, content_type, shikimori_id)` и отмечает
   досмотренную серию в `watched_episodes`. RLS гарантирует, что пользователь
   пишет только свои строки.
4. При открытии серии сервер читает прогресс и, если он для этой серии и
   позиция в допустимом диапазоне, передаёт `start_from` плееру и показывает
   тост «Вы остановились на …».
5. Supabase Realtime уведомляет другие открытые вкладки об изменениях
   (last-write-wins по `updated_at`).

## Критерии приёмки (сценарий)

Вход на ноутбуке → поиск → просмотр серии 3 до 14:32 → закрыть вкладку → вход
на телефоне под тем же аккаунтом → на главной карточка «Серия 3» → клик →
плеер открывается на серии 3 с ~14:32 (допуск ±15 сек).
